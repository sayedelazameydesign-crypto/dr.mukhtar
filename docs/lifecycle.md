## اتجاه التشغيل الذاتي — مراحل لا وعود تشغيل

1. **الأساس:** الاختبارات المحلية والبروفة ببيانات وهمية أولًا. لا تأكيد بلا موافقة موظف
   وحفظ حدث Calendar والتحقق منه؛ فشل الإشعار لا يلغي الحجز. الخصوصية وحماية التهيئة
   والمصادقة والنسخ والاستعادة prerequisites قبل الاعتماد على الأتمتة.
2. **التجهيز والنشر:** تصميم إعداد معزول لكل عيادة وتفويض Google صريح وحفظ أسرار آمن؛
   لا تُدخل مفاتيح في نموذج عام أو رابط. لا نشر تلقائي لكل العيادات: اختبارات، نسخة مثبتة،
   تجربة محدودة، موافقة، ثم نشر تدريجي مع إيقاف ورجوع واختبار استعادة. لا يثبت البناء النشر.
3. **المراقبة والتنبيهات:** تقرير الموظف الحالي يفحص تهيئة وSheets وطوابير ومجرد العثور
   على Calendar؛ لا يثبت صلاحية كتابة الأحداث، أو Webhook أو Meta. قبل مراقبة مجدولة يجب
   تصميم مسار موثّق وآمن، وفحص التقادم والمهل والحالة المجهولة وتكرار التنبيهات، واختبار
   قناة التنبيه دون بيانات شخصية. لا توكن في URL ولا اعتبار HTTP 200 وحده دليل صحة.
   أُضيف `evaluateHealthSnapshot_` كتقييم محلي منفصل: يقبل تقرير `healthCheck_` ووقتًا
   وحدًا أقصى للعمر يحددهما المستدعي؛ يصنف التقرير القديم أو المستقبلي أو الناقص أو المتناقض
   `unknown`، ولا يعيد نصوص تفاصيله. لا يجلب بيانات ولا يرسل تنبيهًا أو يُجدول نفسه. نجاح
   الفحوص الموجودة ليس دليل جاهزية شاملة؛ ولم تُنفّذ مصادقة المصدر أو سياسة التنبيه والتكرار.
   مسار `?health=liveness` عام وثابت، لا يقرأ الإعدادات أو الخدمات ولا يمثل فحص صحة شاملًا.
   الدالة الخاصة `runHealthMonitorOnce_` تعمل فقط عند استدعاء خادم موثوق؛ تسجّل وقتًا
   ورموزًا ثابتة في ورقة `Monitoring` موجودة مسبقًا برؤوس `checkedAt, state, reason,
   failedChecks`، وترفض الورقة المفقودة أو المخالفة دون تعديلها. لا تنشئ مشغّلًا ولا تُرسل
   بريدًا، ولا تتوفر بعد سياسة احتفاظ أو تنبيه عند تعذّر التسجيل. لم تُختبر على Google حي.
4. **العمليات والمساعدة:** ملخص يومي وتذكيرات ورسائل تتطلب تصميم موافقة وخصوصية وتفادي
   التكرار واختبارات واعتمادًا منفصلًا قبل أي إرسال. صفحة مساعدة إدارية لا تجمع أعراضًا ولا
   تعطي نصائح طبية. Dependabot وRenovate مهيآن في المستودع؛ تفعيلهما الفعلي غير مثبت هنا.

تفويض الطبيب وموافقة الموظف والتعامل مع الأخطاء الملتبسة تبقى قرارات بشرية؛ لا يضمن هذا
المخطط «صفر تدخل» ولا يثبت جاهزية الإنتاج. لا تسوية أو حذف تلقائي لأحداث مشتبه بها دون دليل.

## الفجوة بين هذه الصفحة و«منتج يعمل»

المراحل ١–١٢ **مغلقة بدليل**. المراحل ١٣–١٨ **مفتوحة جميعًا**، والسبب واحد لا ستة:
**لم يمرّ طلب حقيقي واحد من صفحة إلى تقويم عيادة.** كل ما تبقّى يصبّ في إغلاقها:

1. بيانات العيادة: **رقم الترخيص** (لا يُخترع؛ اسم الطبيب مُدخل، والترخيص إعفاء مؤقت حتى توفّره).
2. `initializeCeliaKids()` في حساب Google → ٣ أوراق + تقويم.
3. نشر Web app (Execute as Me / Anyone) + رفض الرمز الخطأ.
4. **البروفة السبع** B5.1–B5.7 على هاتف حقيقي → تُغلق `G1` و`G14`.
5. بعدها فقط: تصميم مسار مراقبة آمن ومختبر وتنبيه مناسب، ونسخة احتياطية/استعادة مُختبرة، ووسم `v1.0.0`. `doGetHealth` ليس مسارًا جاهزًا للربط.

> **القاعدة المطبَّقة هنا:** «لا تعتبر نجاح النشر دليلًا على نجاح التطبيق». لذلك المرحلة ١٦
> (`PRODUCTION VERIFICATION`) تبقى 🟡 حتى يظهر `live.appsScript` بحالة PASS من تشغيل حقيقي —
> والفحص المحلي لا يستطيع منحها هذه الحالة، بالتصميم.
