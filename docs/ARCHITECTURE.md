# Architecture Blueprint v1.0 — مسودة خطة المنصة

**التاريخ:** ٢٠٢٦-١١-٠٧ · **الحالة:** مقترح للتوثيق والمراجعة، وليس نظامًا منفذًا أو إذنًا
بنشر أو نقل بيانات. هذه الوثيقة تصف وجهة محتملة تدريجية؛ لا تستبدل خريطة الكود الحالي
[docs/map/ARCHITECTURE.md](map/ARCHITECTURE.md)، أو [سجل الجاهزية](production-readiness.md)،
أو قواعد [AGENTS.md](../AGENTS.md). عند التعارض بشأن ما هو منفذ اليوم يُرجع إلى الكود والاختبار
والوثائق المختصة، لا إلى مخطط مستقبلي. لا يُعتمد تغيير في التخزين أو السياسة أو الأذونات ضمنًا.

## ١. الهدف والنطاق

- المرحلة الأولى: بيانات إدارية **وهمية فقط**، استعراض مواعيد اليوم، ومراجعة بشرية؛ لا تشغيل
  لمرضى حقيقيين، ولا شبكة أو مزوّد أو مفاتيح في النموذج المحلي المقترح. لا إرسال أو إنشاء
  مشروع أو تعديل أصول Google حية دون موافقة منفصلة.
- المشروع الحالي لعيادة واحدة. التوسع لأطباء وعيادات متعددة متطلب مستقبلي، لا خاصية منفذة؛
  يحتاج عزلًا فعليًا للمستأجرين واختبارات فصل بيانات وصلاحيات مستقلة قبل التخطيط لتشغيله.
- لا بيانات طبية، تشخيص، أدوية، أعراض، أو سجلات مرضى في النظام أو الروابط أو السجلات أو
  نماذج الذكاء الاصطناعي. أي تغيير لهذا الحظر يستلزم قرارًا وتصميمًا ومراجعة قانونية وأمنية
  منفصلة، ولا تشمله هذه الخطة. لا يعتمد الحجز على AI.
- لا وعد بتشغيل بلا أخطاء أو توفر دائم أو تكلفة صفرية بلا حدود، ولا يُعتبر نجاح الفحوص وحده
  إثباتًا للسلامة. الفشل غير المعروف يُعرض للمستخدم بدل ادعاء النجاح أو القائمة الفارغة.

## ٢. أين نحن وما الذي لم يُبنَ

| المكوّن | الموجود في المستودع | ما هو مقترح فقط |
| --- | --- | --- |
| الواجهة | `app.js` مع ديمو منفصل يعتمد `localStorage`، ومسار GAS منفصل. البيانات في الديمو على الجهاز وليست بيانات مشتركة. | نموذج واجهة آمن للأطباء، وربما Next.js/React/Tailwind بعد تقييم مستقل؛ لم تُعتمد هذه التقنيات. |
| الخادم | `Code.gs`، وSheets وCalendar عبر Apps Script؛ حالة النشر الفعلي غير متحققة. | Node/Express أو Supabase أو بوابة منفصلة خيارات غير منفذة ولا مرخصة للاستخدام الحي. |
| المواعيد | تقديم طلب قد ينتهي `REQUESTED` أو `PENDING_APPROVAL`؛ موافقة الموظف هي مسار التأكيد. عدة طلبات معلقة لنفس الوقت ممكنة حاليًا. | نموذج حالات ومزامنة أدناه، واختبارات تعارض ومراجعة أوسع؛ ليس تعديلًا للسياسة الحالية. |
| الملخص | `generateDailySummary` يقرأ طلبات اليوم المؤكدة ويتطلب جلسة موظف؛ لا يتحقق من Calendar. صف بدون `eventId` يُستبعد ويُحذّر منه. | التحقق المستقل من الحدث والتسوية؛ وجود `eventId` وحده ليس إثباتًا لبقاء الحدث. |
| الرسائل | كود GAS يحضّر روابط يدوية مقيدة بالحالة، والديمو لا يولّد روابط للمستلمين. فتح الرابط ليس إرسالًا. | سجل حالة مستقل للرسائل ومؤشر بشري، غير منفذين؛ إرسال API متوقف حتى تصميم وموافقة منفصلين. |
| Google والبروفة | نماذج واختبارات محلية؛ الأدلة لا تثبت سلوك Apps Script المنشور. | مشروع اختبار مستقل وبروفة معزولة لاحقًا، بعد مطابقة المسارات والموافقة. |

النماذج المحلية في `scripts/` ليست موصولة بالواجهة أو آلية قفل في Google؛ انظر
[تدقيق الحالة المركبة](composite-status-parity-audit.md) و[مواصفة الأعطال](operational-slot-fault-spec.md).
لا تضف حالة مركبة إلى Sheets الحالي أو تغيّر ترويساته اعتمادًا على هذه الوثيقة.

## ٣. الحالات المقترحة وحدود الانتقال

الأسماء التالية **نموذج مفاهيمي** وليست قيمًا مقبولة حاليًا في `Requests`؛ يلزم تصميم
ترجمة ومهاجرة متوافقة مع كل المستهلكين قبل أي تنفيذ. حالات الطلب والموافقة والرسالة مستقلة.

| حالة الطلب المقترحة | معناها | انتقال مسموح تصوريًا / شرطه |
| --- | --- | --- |
| `DRAFT` | بيانات وهمية محلية لم تُرسل للمراجعة. | إلى `PENDING_REVIEW` بفعل واضح وبعد تحقق محلي. ليست حجزًا أو حجزًا حصريًا للفترة. |
| `PENDING_REVIEW` | طلب ينتظر موظفًا؛ قد توجد عدة طلبات على نفس الفترة. | موافقة موظف مخوّل وفحص التعارض والحدث وحفظ النتيجة المؤكدة؛ أو إلغاء/اقتراح تعديل. لا وعد بحجز تلقائي. |
| `CONFIRMED` | تأكيد من النظام الأساسي بعد الموافقة وحفظ حدث تقويم متحقق منه وفق البروتوكول المعتمد. | إلغاء أو تعديل مصرح به أو إكمال؛ النتيجة الملتبسة لا تتحول لنجاح. |
| `CANCELLED` / `COMPLETED` | حالة نهائية وفق إجراء الموظف والقواعد المعتمدة. | حقوق البيانات والتقويم تحتاج مسارًا مصرحًا منفصلًا. |
| `NEEDS_REVIEW` / `UNKNOWN` | نموذج مقترح لحالة غير محسومة أو تحذير مستقل، بحسب تصميم التخزين المستقبلي. | مراجعة بشرية محمية؛ لا إعادة عمياء ولا تحرير حجز أو حذف حدث بالمهلة. لا نفترض أنها حُفظت فعلًا عند فشل الكتابة. |

`RESCHEDULED` في النظام الحالي اقتراح لطلب لم يُؤكّد، لا تأكيدًا لانتقال حدث فعلي. لا تُفترض
مطابقته لأي حالة مستقبلية دون جرد كل المسارات. مراجعة الإلغاء والنقل والإغلاق والحذف وsync
إلزامية. عدم إظهار حالة مركّبة أو حفظ أثرها الذري في الاختبارات الحالية مانع للنشر.

### حالة تذكير منفصلة — مقترح غير منفّذ

| الحالة | المعنى المقترح |
| --- | --- |
| `UNSENT` | لم تُسجّل علامة بشرية للإرسال؛ لا إثبات على وجود أو عدم وجود رسالة خارج النظام. |
| `MANUAL_DRAFT_READY` | مسودة قليلة البيانات أعدت للمراجعة، لا تُرسل تلقائيًا. |
| `SENT_MANUAL` | **إقرار بشري** أنه أرسل، لا إثبات مستقل للإرسال أو التسليم أو القراءة. |
| `UNKNOWN` | للمستقبل إذا لم تُعرف نتيجة قناة إرسال، لا إعادة تلقائية. |

مراجعة الرسالة والإرسال يقوم بهما الموظف صراحة في واتساب؛ فتح `wa.me` ليس إرسالًا أو موافقة
على الإرسال. الروابط لا تتضمن نوع الزيارة أو بيانات صحية؛ رقم المستلم ونص الرسالة يظهران للقناة
والمتصفح ويحتاجان مراجعة الخصوصية والموافقة. الرابط اليدوي لا يضمن تجنب الحظر ولا مجانية الشبكة
أو كل خدمات WhatsApp. التركيز على **مواعيد اليوم المؤكدة**؛ الغد ليس ضمن المرحلة الأولى.

## ٤. مصدر الحقيقة والتنافس

1. قبل تصميم المزامنة يُختار **مصدر حقيقة واحد** لكل سجل ونسخة/إصدار وخط تعارض معروفان،
   ويُكتب مسار ترحيل واسترجاع. لم يُختر مصدر جديد؛ لا يُعد `localStorage` أو IndexedDB قاعدة
   مشتركة متعددة الأجهزة أو نسخة احتياطية موثوقة، ولا تُعتبر Sheets تلقائيًا نسخة احتياطية.
   يحتفظ الديمو ببيانات وهمية فقط وقد تُفقد أو تختلف بين الأجهزة أو الألسنة.
2. التأكيد الحقيقي المقترح يحتاج آلية تنافس متوافقة مع **كل الكتاب**: قراءة موثوقة، تحقق من
   النسخة والفترة داخل قفل أو معاملة قصيرة مناسبة للمخزن، حجز/مطالبة موثوقة، ثم معالجة النتيجة
   وتسويتها. القفل أو optimistic locking ليس ضمانًا دون اختبار التخزين والكتّاب والتوقف. لا
   يُحفظ القفل عبر Calendar أو شبكة؛ بعدها تُعاد قراءة الحالة تحت قفل قصير. التغييرات المباشرة
   خارج النظام تحتاج سياسة ووسيلة اكتشاف مستقلة، ولا يغطيها قفل التطبيق.
3. الطلبات المعلقة المتعددة الحالية سياسة منفصلة عن تعارض التأكيد. فرض نجاح تقديم طلب واحد
   للفترة الواحدة تغيير سياسة واعٍ يتطلب موافقة، لا نتيجة مفترضة في البروفة.
4. `SpreadsheetApp.flush()` لا ينشئ معاملة بين Sheets وCalendar، ونجاح استدعاء أو حفظ
   `eventId` وحده ليس إثباتًا شاملاً. فشل القراءة لا يثبت غياب حدث. كتابة أو نتيجة ملتبسة تبقى
   محجوبة للمراجعة؛ لا يُحذف حدث تلقائيًا ولا تتحرر مطالبة عالقة حسب عمرها.
5. آلية nonce أو idempotency المقترحة تحتاج مصادقة وحفظًا دائمًا وعلاقة قابلة للإثبات مع
   المحاولة، وتصميم عزل واسترداد. رفض nonce مكرر لا يقرر نتيجة المحاولة الأصلية. النماذج
   الحالية في الذاكرة لا تثبت ذرية أو حجزًا دائمًا أو أمان تحرير بشري.
6. الطابور أو تجميع التحديثات وحدهما لا يمنعان التعارض أو فقد البيانات أو تجاوز الحصص؛ يلزم
   تصميم أحجام وحدود وتشغيل وتفويض وأخطاء ونسخ احتياطية واسترجاع وفحص حالة الكتابة قبل الإعادة.

## ٥. الخصوصية والأمن والاحتفاظ

- بيانات الاختبار مصطنعة بوضوح، بلا مفاتيح أو أرقام حقيقية أو معلومات صحية، ولا تُرسل إلى
  أي خدمة. لا يعتمد النموذج المحلي على GitHub Secrets أو Script Properties أو حساب Google.
- تشفير التخزين المحلي، وحماية المفاتيح، والمصادقة، وإدارة الجلسات، وRBAC، وعزل العيادات
  **متطلبات تصميم واختبار مستقبلية** وليست ضمانات مفعلة في الديمو. مجرد تشفير المتصفح لا
  يحمي من XSS أو مستخدم مصرح له على جهاز مشترك؛ يلزم تصميم تهديدات ومفاتيح وصلاحيات فعلي.
- جمع الحد الأدنى ونسخة نص الموافقة ووقتها لكل طلب متطلب للمستقبل، وكذلك سحب موافقة التواصل.
  لا تحفظ بيانات طبية؛ لا معلومات تعريفية أو أسرار في logs أو artifacts أو نصوص مرسلة إلى AI.
- الاحتفاظ التلقائي في الكود المحلي متوقف افتراضيًا؛ حالة النشر الفعلي غير متحققة. قبل أي تفعيل:
  تحديد المدة مع الطبيب/المحامي، فحص جاف، نسخ احتياطي بصلاحيات وعمر محددين، واختبار استعادة
  وحذف وفشل Calendar. إصدارات Sheets وسلة Drive قد تبقى بعد الحذف؛ لا يُفترض محو فوري.
- قبل أي بيانات حقيقية يلزم تقييم الخصوصية والأمن والقوانين المحلية وحماية البيانات في مصر
  والدول المستهدفة، واعتماد الاختصاصات ونقل البيانات مع مختص قانوني؛ هذه الوثيقة ليست استشارة قانونية.

## ٦. الفشل والتشغيل والتكلفة

| الفشل | السلوك التصوري الآمن |
| --- | --- |
| تعذرت قراءة الطلبات أو Calendar | تحذير واضح و`UNKNOWN`؛ لا قائمة فارغة مضللة أو تأكيد أو استنتاج أن الفترة خالية. |
| ضاع الرد أو فشلت كتابة بعد احتمال تطبيقها | مراجعة بشرية وحجب ما يلزم؛ لا إعادة تلقائية أو حذف أحداث. |
| فشل إعداد أو إذن أو استنفدت حصة | لا تحويل صامت إلى إرسال حي؛ أوقف العملية المتأثرة، وبيّن إجراءً آمنًا للموظف. |
| عدم توافق بين مصدرين | اعرض عدم الاتساق للمراجعة؛ لا تختَر نتيجة حسب تخمين أو تحذف حدثًا تلقائيًا. |
| فشل فحص CI/Scorecard أو خدمة توقيع | احتفظ بحالة الفشل ودليلها؛ Artifact محتمل للتشخيص لا يثبت نجاح التوقيع أو يضمن وجود الملف. |

أي خدمة جديدة تحتاج مراجعة تكلفتها وشروطها وتاريخ إعادة التحقق وبديلها وقرار الخصوصية قبل
اعتمادها، مع سياسة عدم إدخال بطاقة. حدود Google وGitHub وغيرها متغيرة وبحسب الحساب؛
[سجل الخدمات](free-tiers.json) لقطة لا ضمان، وتُراجع الشروط قبل التنفيذ. استضافة Pages لها
قيود تجارية وحساسية بيانات؛ راجع [خطة ٢٠٢٦](plan-2026-finish.md) قبل أي إطلاق. لا تسجيل
حسابات أو إنشاء صلاحيات أو فواتير في هذه المرحلة.

## ٧. اختبارات ومعايير الانتقال

1. **مواصفات محلية:** نموذج وبيانات وهمية فقط؛ اختبار انتقالات الحالات والرفض والقراءة الفاشلة
   وظهور التحذيرات وحالات التخزين الملتبس. محاكاة نافذتين تفيد في كشف أخطاء الواجهة لكنها ليست
   برهانًا على تزامن خوادم أو أجهزة حقيقية. اختبارات القاهرة وDST والفترات المتداخلة، وأنواع
   خلايا Sheets والقراءات والأعطال ضمن المتطلبات، لا إنجاز مفترض.
2. **مطابقة المسارات:** مراجعة جميع مسارات الحجز، التعديل، الإلغاء، الإغلاق، الحذف، sync
   واللوحة. `node scripts/probe-composite-paths.js` تشخيص محدود؛ خروجه 1 يعني بقاء حالات غير
   متوافقة، ونجاحه وحده لا يثبت سلامة بقية الحالات. لا نقل للحالة المركبة إلى Google قبل الحل.
3. **بروفة Google، لاحقًا بموافقة منفصلة:** مشروع Apps Script وSheet وCalendar مستقلة عن
   الإنتاج، بيانات وهمية، وثلاث جولات تنافس منفصلة لكل منها ١٠ طلبات `fetchAll` حقيقية لنفس
   الفترة بمراجع/أرقام اختبار مختلفة. قراءة الصفوف والأحداث ونتائج كل محاولة شرط؛ لا تُستنتج
   النتيجة من HTTP 200 فقط. اختبارات حقن الأعطال منفصلة عن التنافس. تصميم وسياسة نجاح تأكيد
   واحد لا يعني تغيير قبول الطلبات المعلقة دون قرار واضح.
4. **قبل المرضى:** مراجعة قانونية وأمنية، إثبات العزل، الاستعادة، الصلاحيات، الأذونات، الفشل
   والتحذيرات، تسوية تقويم بدون حذف آلي، وتشغيل بروفة مستقلة ناجحة. حتى ذلك الحين الجاهزية
   `not-ready`، والواجهات الحية والإرسال متوقفان في نطاق هذه الخطة.
5. **البناء والرجوع:** ملف المصدر في الجذر هو مرجع البناء، والأمر
   `python3 scripts/build-gas-package.py` ينتج حزمة `gas/`؛ لا يثبت هذا تطابق النسخة المنشورة.
   قبل نشر لاحق يلزم فحص اختلاف ناتج البناء عن المنشور بوصول حقيقي، وتسجيل Deployment ID
   والنسخة المنشورة المعروفة وخطوات rollback في `RELEASES.md`، ثم موافقة منفصلة على النشر.

## ٨. قرارات مفتوحة

- هل يوجد احتياج فعلي لتعدد العيادات، وما نموذج عزل البيانات والمفاتيح وتكلفة التشغيل؟
- ما مصدر الحقيقة المقبول، وكيف يُضمن التعارض والاسترجاع والتعامل مع المحاولة الملتبسة؟
- هل تُعتمد تقنيات واجهة أو خادم أو قاعدة بيانات جديدة بعد مراجعة الحدود والشروط والبدائل؟
- من يجيز الاستضافة والاحتفاظ والموافقة والقوالب والصلاحيات؟ وما الخطة عند انتهاء الحصص؟
- كيف توثَّق مراجعة بشرية آمنة للمطالبة العالقة دون تحرير تلقائي أو حذف حدث تقويم؟

الخطوة التالية الممكنة بعد مراجعة هذه المسودة: **مخطط بيانات وهمي محلي فقط**، مع بقاء الأسئلة
وحدود التنفيذ مفتوحة؛ لا يغيّر الكود الإنتاجي أو المخططات الحالية تلقائيًا.
