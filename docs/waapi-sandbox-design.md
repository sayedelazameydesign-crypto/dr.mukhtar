# تصميم WAAPI للتجربة فقط — لا تشغيل حي

**الحالة:** هذا التغيير لا ينشر endpoint ولا ينفّذ استقبالًا أو إرسالًا حقيقيًا؛ وضع نشر
Apps Script الفعلي غير متحقق. في الشفرة المحلية توجد
دالتان خاصتان داخل `WhatsApp.gs`: `waapiSandboxPreview_` تنتج مثالًا ثابتًا بوجهة غير
صالحة، و`waapiClassifyResponse_` تصنّف استجابة دون كشف محتواها أو إثبات تسليم. لا تقرآن
أسرارًا ولا تتصلان بالشبكة ولا تتصلان بمسار الحجز أو الإرسال. الاختبار:
`node scripts/test-whatsapp-adapter.js`. الاتجاه المختار هو تجربة WAAPI ببيانات وهمية
ورقم الاختبار المصرّح به فقط بعد موافقة منفصلة، ثم تقييم واجهة Meta الرسمية قبل التعامل
مع المرضى. WAAPI مستقل وليس واجهة Meta الرسمية؛ تغيير المزوّد يحتاج اختبارات واعتمادًا
جديدين ولا يضمن منع الحظر أو انعدام الكلفة.

## الأدلة والحدود

- فحص Actions السابق نجح في `GET /instances` فقط؛ لم يثبت ربط رقم أو صلاحية إرسال
  أو اتصال Webhook. `WAAPI_API_TOKEN` في GitHub Actions لا يُحقن تلقائيًا في Apps Script.
- يوجد فحص اختياري للرقم التجريبي المسجل في `developerPhone` بملف `clinic.json` عبر `Setup status`؛
  يتطلب تفعيل `check_test_contact` صراحة في التشغيل اليدوي، وهو متوقف افتراضيًا. يقرأ معلومات
  العميل وحالته فقط عندما يظهر instance واحد، ويقارن الرقم دون طباعة رقم أو توكن أو استجابة.
  غياب instance أو تعدده أو فشل القراءة يعيد `UNKNOWN` لا حكمًا على الاتصال. `CONNECTED` لقطة
  حالة وليست إثبات إرسال أو تسليم، والفحص لا ينشئ instance أو يربط رقمًا أو يرسل رسالة.
- [توثيق WAAPI للـWebhook](https://waapi.readme.io/reference/webhooks) يعرض مثالًا
  يعتمد سرًا داخل مسار URL. في المقابل يذكر [موقع WAAPI](https://waapi.app/small-business)
  توقيع HMAC دون تحديد الترويسة أو خوارزمية/تمثيل التوقيع في هذا الوصف. **عقد التوقيع
  للـinstance الفعلي غير متحقق**: لا نختلقه ولا نستبدله بتوقيع Meta. لا نضع أسرارًا
  داخل URL أو السجلات أو المستودع.
- حدث `message` موصوف في [مرجع WAAPI](https://waapi.readme.io/reference/message-event)
  ويتضمن هوية المرسل والنص، وقد يتضمن محتوى حساسًا. هذا ليس إذنًا بنشر أو استقبال.
- Google لا توثّق ترويسات الطلب في [حدث Apps Script Web App](https://developers.google.com/apps-script/guides/web).
  أي توقيع يعتمد ترويسة يتطلب نقطة استقبال تدعمها بوضوح، ثم وصلة موثّقة مستقلة
  إلى التطبيق. لا يُسمح بتجاوز التحقق لمجرد نجاح طلب GET من المزوّد.

## حدود مقترحة للمكونات

```text
WAAPI
  → نقطة استقبال HTTPS [غير منفّذة: توثيق الطلب قبل المعالجة]
  → محوّل أحداث [تحقق من instance، النوع والمرسل + منع التكرار]
  → منطق طلب المواعيد [بيانات إدارية فقط؛ REQUESTED/PENDING_APPROVAL]
  → موافقة موظف + تحقق Calendar وحفظه
  → قائمة انتظار إشعار [اختبار محصور، أو off؛ مستقلة عن الحجز]
  → محوّل المزوّد [WAAPI للتجربة / Meta الرسمية لاحقًا]
```

- لا يستخدم المزوّد أو النموذج `approveRequest` أو ينشئ حدث تأكيد تلقائيًا؛ هذا الإجراء
  يبقى لموظف مخوّل. فشل الإشعار لا يلغي أو يعيد محاولة تأكيد الحجز.
- لا تُخزّن نصوص واردة حرة أو وسائط أو معلومات طبية. لا ترسلها إلى Gemini. إن استُخدم
  نموذج مستقبلًا فهو اختياري، يتلقى مدخلًا إداريًا مُنقّى فقط، ويُتحقق من مخرجاته كبيانات
  غير موثوقة، والحجز يظل يعمل دونه.
- إعدادات sandbox تحصر المرسِل والمستلم في رقم اختبار مصرح به. عند غياب التقييد أو تعارض
  البيئة أو عدم القدرة على التحقق من التوقيع تُرفض المعالجة/الإرسال؛ لا رجوع إلى الوضع الحي.
  لا يُكتب الرقم الحقيقي في الكود أو الاختبارات أو السجلات. أي رسالة اختبار لا تحتوي إلا
  بيانات وهمية، ولا تُحوّل بيانات أولياء الأمور إلى بريد المبرمج.
- منع التكرار يجب أن يستخدم معرّف الحدث أو الرسالة المثبت في عقد المزوّد، مع تخزين دائم
  وحدود عمر وآلية ذرّية. لا يُعتبر قبول API دليل تسليم، ولا تُعاد محاولة إرسال ملتبسة
  بصورة عمياء. ACK منفصل يحدّث الحالة بعد التحقق.
- التذكير يحتاج موافقة واتساب منفصلة قابلة للسحب، إعادة فحص حالة الموعد ووقته، منطقة
  `Africa/Cairo`، ومفاتيح منع تكرار مناسبة. لا يوجد مُجدول آمن لهذه الخاصية حاليًا.

## مراحل التنفيذ ومعايير المرور

1. **محاكاة بلا شبكة:** اختبارات أحداث صالحة/غير صالحة، مرسل آخر، مجموعات، وسائط، أحداث
   ذاتية، تكرار وتزامن، فشل التخزين، صيغة تالفة، وعدم تخزين أو تمرير النص الحر؛ مع
   اختبارات لرفض أمثلة طبية معروفة دون ادعاء أن مرشّح النص يكشف كل الحالات.
2. **حد استقبال موثّق:** تثبيت عقد توقيع WAAPI الفعلي وعقد الربط إلى Apps Script؛ اختبار
   الأجسام الخام والترويسة الصحيحة والمفقودة والمعدّلة والهجمات المعادة، مع فشل مغلق.
   لا نشر إلى العامة قبل مراجعة هذا الحد وخطة رجوع.
3. **بروفة Google:** إثبات الربط الحقيقي بين نسخة Apps Script والموارد، وموافقة الموظف
   وحفظ Calendar، وتسوية الحالات الملتبسة، دون استخدام بيانات مرضى فعلية.
4. **تجربة محدودة:** موافقة منفصلة على الإرسال، تحديد حصة وكلفة ووجهة واحدة، وفحص
   استجابة الإرسال والتسليم بشكل مستقل. تشغيل الإشعارات والتذكيرات يظل متوقفًا افتراضيًا.
5. **قبل الإنتاج:** اعتماد قناة Meta الرسمية واختبار Webhook والقوالب والموافقة والتكلفة
   والخصوصية والصلاحيات وحذف البيانات من جديد. لا يُفترض أن توكن WAAPI أو عقود Webhook
   أو قرارات التسعير قابلة للنقل إلى Meta.

لا يقتضي هذا التصميم تسجيل خدمة إضافية أو إدخال مفتاح في المحادثة. تظل تفاصيل حساب
Meta وإعدادات ومخرجات Apps Script والربط الفعلي غير متحققة حتى تتوفر أدلة مناسبة.
